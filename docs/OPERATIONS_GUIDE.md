> **ما هذا الملف؟** دليل عملي واحد يجمع: كيف تُشغّل النظام على جهازك أو على خادم، وكيف
> تستخدمه وحدةً وحدة (محاسبة، مخزون، مبيعات، مناديب، ضريبة/ZATCA، تقارير، مساعد ذكي)، وكيف
> تُدار المنصة (الخطط، التنبيهات، النسخ الاحتياطي والاستعادة)، وما هي **حدود هذا الإصدار**

> (التشطيب والجاهزية للإصدار) جارية — تقرير الجاهزية في `docs/RELEASE_READINESS.md`،

## 1. تشغيل سريع (Quick start)

### 1.1 المتطلبات

| المتطلب | الإصدار / الملاحظة |
|---|---|
| Node.js | 22.x (مُختبَر على 22.22) |
| قاعدة بيانات | أي PostgreSQL حديث (15+)، أو قاعدة التطوير المدمجة في الساندبوكس |
| متغيرات البيئة | ملف `.env` في جذر المشروع (غير مُتتبَّع في Git) |
| حزم النظام | لا شيء إلزامي — تُستخدم مسارات `pg_dump`/`psql` اختيارية (يُستخدم البديل المنطقي عند غيابها) |

### 1.2 أول تشغيل (أمر واحد للتجهيز)

```bash
cd ERPCloud3
npm install                      # تثبيت الحزم
cp .env.example .env 2>/dev/null || true   # ثم عدّل القيم (انظر الجدول في §1.5)

# قاعدة بيانات التطوير (ساندبوكس بلا PostgreSQL مثبَّت):
node scripts/dev-postgres.mjs --dir .pglite   # نافذة طرفية مستقلة، يبقى يعمل

# تجهيز المخطط + سياسات RLS + البيانات التجريبية (⚠️ أمر مُدمِّر: يمسح قاعدة البيانات):
node scripts/db-reset.mjs
```

`db-reset.mjs` ينفّذ بالتسلسل: **إسقاط → `drizzle-kit push` → تطبيق `src/db/rls.sql` → `seed.ts`**.
إن أردت التنفيذ يدويًا على قاعدة بيانات حقيقية:

```bash
npx drizzle-kit push                   # إنشاء/تحديث المخطط من src/db/schema.ts
psql "$DATABASE_URL" -f src/db/rls.sql # سياسات عزل المستأجرين (طبقة الدفاع الثانية)
npx tsx scripts/seed.ts                # البيانات الأساسية + منشأتان تجريبيتان
```

### 1.3 تشغيل التطبيق

```bash
npm run dev            # تطوير: http://localhost:3000  (Turbopack)
# أو نسخة شبيهة بالإنتاج:
npm run build && npm start
```

| العنوان | الغرض |
|---|---|
| `http://localhost:3000/login` | دخول مستخدمي المنشآت (الشاشة الرئيسية للنظام) |
| `http://localhost:3000/platform/login` | دخول **منصة الإدارة** (نطاق جلسة منفصل تمامًا) |
| `http://localhost:3000/api/health` | فحص الصحة (قاعدة البيانات، العمليات، حداثة النسخ الاحتياطي) |
| `http://localhost:3000/api/sync` | نقطة مزامنة المناديب (تُستخدم من التطبيق الميداني) |

### 1.4 الفحص السريع بعد التشغيل

```bash
curl -s localhost:3000/api/health | head -40     # يجب أن يعيد {"status":"ok", ...}
npm run typecheck                                # فحص الأنواع
npm test                                         # كل الاختبارات (يحتاج .env محمَّلًا)
npm run acceptance:sweep -- --soak=20            # مسح قبول شامل على كل الشاشات (39 فحصًا)
```

> **ملاحظة مهمة قبل `npm test`:** الاختبارات التكاملية تحتاج متغيرات البيئة، شغّلها هكذا:
> `set -a && . ./.env && set +a && npm test`.

### 1.5 متغيرات البيئة

| المتغير | إلزامي | الوصف |
|---|---|---|
| `DATABASE_URL` | ✅ | رابط PostgreSQL (`postgresql://user:pass@host:5432/dbname`) |
| `HISAB_ENCRYPTION_KEY` | ✅ | مفتاح تشفير (32 بايت) لحفظ **المفاتيح الخاصة لـ ZATCA** وبيانات الاعتماد؛ فقدانه = فقدان القدرة على التوقيع بشهادات قائمة |
| `ENABLE_WORKER` | — | `true` لتشغيل معالج المهام الخلفية (pg-boss). في الساندبوكس `false` لأن المحرّك المدمج لا يدعم `LISTEN/NOTIFY` |
| `PG_POOL_MAX` | — | أقصى عدد اتصالات بالحوض (اتركه صغيرًا مع المحرّك المدمج) |
| `LOG_LEVEL` | — | `debug | info | warn | error` |
| `SEED_PLATFORM_EMAIL` / `SEED_BOOTSTRAP_PASSWORD` | للتهيئة | بريد وكلمة مرور **مالك المنصة** عند أول `seed` |
| `SEED_DEMO_PASSWORD` | للتهيئة | كلمة مرور المستخدمين التجريبيين |
| `ASSISTANT_API_KEY` | — | مفتاح مزوّد المساعد الذكي. التطبيق يقرأ **اسم المتغير** فقط (`secretRef`)، ولا يُخزِّن المفتاح في قاعدة البيانات |

> **قاعدة أمان:** لا تُدخل أي مفتاح أو كلمة مرور في واجهة النظام. شاشة إعدادات المساعد تطلب
> **اسم متغير البيئة** (مثل `ASSISTANT_API_KEY`)، والقيمة تُوضع في `.env` على الخادم فقط.

### 1.6 حسابات الدخول التجريبية (بيانات الساندبوكس فقط)

| المستخدم | البريد | الدور | الاستخدام |
|---|---|---|---|

| محاسب | `acc@horizon.test` | محاسبة ومخزون وتقارير | دورة القيود والتقارير |
| مندوب | `rep@horizon.test` | ميداني (نقاط بيع، عهدة، تسوية) | سيناريو المندوب |
| أمين مخزن | `wh@horizon.test` | مخزون | الاستلام والصرف والجرد |
| مالك منشأة ثانية | `owner@nokhba.test` | كل الصلاحيات (منشأة مختلفة) | إثبات العزل بين المنشآت |
| مالك المنصة | `admin@hisab.sa` | منصة (Owner) | لوحة `/platform` |

كلمة مرور المستخدمين التجريبيين = قيمة `SEED_DEMO_PASSWORD` في `.env` (القيمة التطويرية
`Hisab#2026`). كلمة مرور مالك المنصة = `SEED_BOOTSTRAP_PASSWORD`.
**دخول المنصة يتطلب تفعيل التحقق بخطوتين (TOTP)**: إن لم يكن الحساب مُفعَّلًا، ستوجّهك شاشة

## 3. دورة الاستخدام اليومية (وحدةً وحدة)

### 3.1 التهيئة الأولية للمنشأة

1. **شجرة الحسابات** (`/accounting` → الدليل المحاسبي): تُنشأ تلقائيًا لكل منشأة من القالب
   الافتراضي. راجع أسماء الحسابات قبل الترحيل.
2. **ربط الترحيل (Posting Mapping)**: كل حدث محاسبي (بيع، مرتجع، شراء، صرف…) يجب أن يكون له
   حساب مدين وحساب دائن. أي ربط ناقص **يمنع الترحيل برسالة واضحة** ولا يُخمَّن.
3. **الفترة المالية**: افتح السنة/الفترة الجارية. لا يمكن الترحيل في فترة مغلقة.
4. **الصناف والمخازن**: أضف الأصناف (وحدة القياس، الضريبة، الحد الأدنى، طريقة التكلفة)
   والمخازن (بما فيها مخزن الحجر و«بضاعة بالطريق» الافتراضي).
5. **العملاء والموردون**: البيانات الضريبية (الرقم الضريبي/السجل) مهمة للفواتير الرسمية.
6. **المستخدمون والأدوار**: أنشئ المستخدمين ووزّع الأدوار. الصلاحية تُفحص في الخادم عند كل
   عملية، وإخفاء عناصر القائمة ليس حماية.

### 3.2 رأس المال والبداية

- **رصيد افتتاحي للمخزون**: من شاشة المخزون (رصيد افتتاحي) — يقيَّد محاسبيًا حسب سياسة التكلفة.
- **أرصدة افتتاحية للحسابات**: قيد يدوي متوازن (مدين = دائن) بتاريخ بداية السنة.
- القيود اليدوية تُحفظ **مسودة** ثم تُعتمد ثم تُرحَّل (حسب الصلاحيات).

### 3.3 المبيعات

1. `/sales` → «فاتورة بيع جديدة» → العميل، الأصناف، الكميات، الأسعار.
2. «حفظ» (مسودة) أو «حفظ وترحيل». الترحيل ينفّذ في معاملة واحدة: سجل المخزون + التكلفة +
   القيد المحاسبي + الضريبة.
3. الفاتورة بعد الترحيل **غير قابلة للتعديل** — التصحيح يكون بالمرتجع (`sale_return`) أو القيد العكسي.
4. الطباعة: A4 للفاتورة الضريبية، وحراري لنقاط البيع.
5. الفاتورة المبسّطة (بدون بيانات مشترٍ) تُبلَّغ لـ ZATCA (Reporting)، والقياسية تُختم (Clearance) —
   انظر §3.8.

### 3.4 المشتريات

- أمر شراء → استلام (يدخل المخزون) → فاتورة المورد (تلتزم بأمر الشراء) → سند دفع.
- الفرق بين الاستلام والفاتورة يظهر في تقارير المشتريات المعلّقة.

### 3.5 المخزون

| العملية | المسار |
|---|---|
| حركة دخول/خروج | شاشة المخزون → حركة مخزون (نوع الحركة + المستند) |
| تحويل بين المخازن | تحويلات (مسودة → إرسال (بضاعة بالطريق) → استلام) |
| جرد | جلسة جرد → إدخال الكميات المحسوبة → ترحيل الفروق |
| دفعات وانتهاء | تُلتقط عند الاستلام (رقم الدفعة وتاريخ الانتهاء)، والصرف بنظام FEFO |
| رصيد افتتاحي | شاشة الرصيد الافتتاحي |

التكلفة: المتوسط المرجّح (WAC) مع اختيار الدفعات FEFO. لا يمكن أن يصبح الرصيد سالبًا —
النظام يوقف العملية برسالة.

### 3.6 النقد والتحصيل

- الصناديق/البنوك: `/cash` — إيداع، سحب، تحويل بين حسابين.
- التحصيل من العميل: سند قبض يُخصم من فاتورة أو أكثر؛ وتقارير الأعمار (Aging) تُبيّن المتأخر.
- تسوية كشف البنك من الشاشة نفسها مع تسجيل العمولات.

### 3.7 المناديب والبيع الميداني

1. عهدة: صرف بضاعة للمندوب (مخزون «بضاعة المندوب») + فاتورة عهدة.
2. البيع الميداني يعمل **دون اتصال**: يقظة محلية، ثم مزامنة عبر `/api/sync` عند عودة الاتصال.
3. التسوية: عدّ النقد والبضاعة، الفرق يُقيَّد (عجز/زيادة) بموافقة المشرف.
4. كل عملية تحمل مفتاحًا فريدًا (Idempotency) فلا تتكرر عند إعادة المزامنة، وأي تعديل لاحق على
   البيانات المرسلة يُكشف (فحص تجزئة الحمولة).

### 3.8 الضريبة و ZATCA (المهم هنا)

1. **إعداد المنشأة**: `/tax` → إعداد ضريبي (الرقم الضريبي، العنوان، بيانات الفرع، أنواع الأصناف).
2. **مفتاح الجهاز (CSR)**: «توليد مفتاح الجهاز» ينشئ مفتاحًا خاصًا على المنحنى secp256k1 وطلب
   توقيع (CSR) بصيغة ZATCA (قوالب: `PREZATCA-Code-Signing` للتجربة، `TSTZATCA-Code-Signing`
   للساندبوكس، `ZATCA-Code-Signing` للإنتاج). المفتاح الخاص يُشفَّر بمفتاح `HISAB_ENCRYPTION_KEY`.
3. **شهادة الامتثال (CCSID)**: أدخل **رمز OTP** الذي تحصل عليه من بوابة ZATCA (فاتورة) لهذا الجهاز.
4. **الفحوص الستة تلقائيًا**: يُرسل النظام الفواتير النموذجية بالترتيب الإلزامي (قياسية، مرتجع
   قياسي، إشعار مدين قياسي، مبسّطة، مرتجع مبسّط، إشعار مدين مبسّط)؛ نتيجة كل فحص تُحفظ.
5. **شهادة الإنتاج (pCSID)**: تُصدر بعد نجاح الفحوص، ويمكن **تجديدها** لاحقًا.
6. **الإرسال الفعلي**: فاتورة مرسلة → تبليغ (Reported) أو ختم (Cleared) بحسب نوعها. كل حالة
   محفوظة مع استجابة الجهة. وإذا تعذّر الإرسال، تبقى الفاتورة في قائمة الانتظار
   (`zatca-submission`).
7. **QR**: يُبنى من وسوم ZATCA ويُشفَّر قاعدة 5 (TLV) على الحالة الصحيحة (رمز TLV للفاتورة
   الموقَّعة يحتاج بيانات التوقيع؛ لا يُنتج النظام رمزًا غير موقَّع أبدًا).

> **مهم جدًا (شفافية):** في بيئة الساندبوكس لا توجد بيانات اعتماد حقيقية من ZATCA، ولذلك لم
> تُنفَّذ مصافحة كاملة مع بيئة فاتورة. كل ما هو مذكور أعلاه **مُختبَر** بقواعد ZATCA الرسمية
> (المخططات، البنية، القواعد) وبمحاكاة داخلية، لكنه **غير مُتحقَّق منه مع بوابة فاتورة** —
> الحد مسجل باسم `AC-025` في `docs/TESTING_AND_ACCEPTANCE.md`. لا تفترض «جاهز للإنتاج مع
> فاتورة» قبل تشغيل الدورة مرة واحدة على بيئة Simulation ببيانات اعتماد حقيقية.

### 3.9 التقارير

- `/reports` يعرض كتالوج التقارير مجمّعًا: محاسبية (R-01…R-13)، مبيعات (R-20…R-29)،
  مخزون (R-40…R-45 وR-46…R-51)، ضريبية (R-60…R-66).
- كل تقرير له معاملاته (فترة/تاريخ أو «حتى تاريخ») وأبعاده (صنف، عميل، مندوب، فرع…).
- **التصدير Excel (xlsx)** متاح من الشاشة. **تصدير PDF غير مُنفَّذ في هذا الإصدار** (مسجَّل كنقص).
- التقارير التي مصدرها غير موجود في هذا الإصدار تظهر بحالة «غير متاح» مع سببها بدلًا من رقم
  مضلِّل — الالتزام بمواصفات التقارير يمنع «ملء الفراغ» بأرقام غير حقيقية.

### 3.10 المساعد الذكي

1. **التمكين على مستوى المنصة**: من `/platform/flags` فعّل مفتاح `ai_assistant` (الافتراضي مُفعَّل
   عالميًا إن لم يوجد سجل).
2. **التمكين داخل المنشأة**: `/assistant/settings` → تشغيل المساعد، المزوّد (OpenAI/Anthropic
   المتوافق)، الموديل، و**اسم متغير البيئة** الحاوي للمفتاح، ونطاق البيانات، ومدة الاحتفاظ.
   - **نطاق البيانات**: «أرقام مجمّعة وأسماء مُقنّعة» (الافتراضي) أو «السماح بالأسماء الحقيقية
     حسب الحاجة» (يُوسِّع ما يراه الموديل من أسماء عملاء/أصناف عند الحاجة).
3. **الاستخدام**: اكتب سؤالًا بالعربية، مثل «كم مبيعات اليوم؟»، «أرصدة المخزون الأدنى من الحد؟»،
   «من العملاء المتأخرون؟». يظهر تحت كل جواب **الأدوات المستخدمة** (مصدر الأرقام).
4. **أمان الحدود**: كل أداة مرتبطة بصلاحية؛ إن لم تكن تملك الصلاحية تُرفض الأداة ويُسجَّل الرفض
   مع **إشارة تصعيد**. المساعد **لا يعدّل شيئًا**: أي إجراء (قيد محاسبي، تصدير) يُحفظ كـ**طلب
   اعتماد**، وينفّذه إنسان بصلاحية الإجراء من نفس الشاشة (اعتماد/رفض)، ثم يظهر أثر التنفيذ.
5. **حماية الحقن**: أي نص من بيانات العمل أو من المستخدم يحاول إعطاء أوامر للموديل يُسجَّل في
   `ai_injection_flags` ويُغلَّف كبيانات غير موثوقة؛ لا يُنفَّذ.
6. **التدقيق والاحتفاظ**: كل محادثة وأداة وتصعيد محفوظ. المحادثات تُنظَّف بعد مدة الاحتفاظ
   (افتراضي 30 يومًا) بينما تبقى سجلات الأدوات/التصعيد و**طلبات الاعتماد كاملة**.


## 4. إدارة المنصة (Platform console)

**الدخول**: `/platform/login` (نطاق جلسة مستقل؛ جلسة منشأة لا تفتح المنصة والعكس صحيح).

| الشاشة | ما تفعله |
|---|---|
| `/platform` | لوحة مراقبة: عدد المنشآت بحسب الحالة، الإيراد المتكرر **المُعلَن**، استخدام الموارد، عمق الطوابير والرسائل الميتة، **حداثة النسخ الاحتياطي كحالة مانعة** |
| `/platform/tenants` | إنشاء منشأة، دورة الحياة (تجربة → نشِطة ⇄ موقوفة → معطَّلة)، تغيير الخطة، الأعلام لكل منشأة |
| `/platform/tenants/[id]` | ملف المنشأة: الاستخدام والحصص، الاشتراك، طلبات الحذف، الصلاحيات المؤقتة (Support grants)، سجل تدقيق المنصة |
| `/platform/plans` | الخطط والحصص (حدود يُفرض احترامها عند الكتابة) |
| `/platform/flags` | أعلام عامة/خاصة بالمنشأة، بتأثير فوري ومسجَّلة في التدقيق |
| `/platform/alerts` | صندوق التنبيهات: إقرار/إسناد |
| `/platform/backups` | نسخ احتياطي الآن، السجل، التحقّق، الحذف حسب سياسة الاحتفاظ، الاستعادة |
| `/platform/exports` | حزم تصدير بيانات المنشأة (manifest + sha256 + رابط منتهي ومُدقَّق) |
| `/platform/audit` | سجل تدقيق المنصة (سلسلة تجزئة، إضافي فقط Append-only) |

**قواعد يجب معرفتها قبل الاستخدام:**

- **التعليق ليس حذفًا.** المنشأة الموقوفة تصبح **للقراءة فقط + تصدير** (منع الكتابة يُفرض على
  مستوى قاعدة البيانات، لا بالواجهة). كل السجل محفوظ، ولا تُحذف صفوف أبدًا خارج مسار الحذف.
- **لا يقرأ مشغّل المنصة بيانات المنشأة المالية افتراضيًا.** قراءة بيانات منشأة تحتاج **صلاحية
  دعم (Break-glass)**: نطاق محدد، مدة ≤ 24 ساعة، موافقة سلسلتين (منصة + منشأة)، وإظهار مقنّع
  افتراضيًا مع منع التصدير، وكل عرض يُسجَّل في سجل المنصة ويظهر لصاحب المنشأة في سجله.
  **انتحال هوية المستخدم ممنوع**.
- **الاستعادة عملية خطيرة**: تحتاج قاعدة **شخصين** + كتابة اسم قاعدة البيانات نصًّا + تدقيق كامل.
- **الحذف النهائي** مسار من خمس خطوات: طلب → عرض التصدير → تأكيد مكتوب → مهلة تبريد → تنفيذ
  (مع احترام مدد الاحتفاظ القانوني) → شهادة حذف.

## 5. العمليات اليومية (النسخ الاحتياطي والمهام)

```bash
npm run backup:run        # نسخة احتياطية فورية (مشفّرة) + بيانات مَنيفست
npm run backup:list       # سجل النسخ
npm run backup:status     # حالة الحداثة والتحقق
npm run backup:verify     # تحقّق فعلي: فك التشفير + مطابقة التجزئة + إعادة تعداد الصفوف
npm run backup:drill      # تمرين استعادة في مخطط معزول (restore_drill_*) ثم حذفه
npm run backup:prune      # حذف ما تجاوز سياسة الاحتفاظ
```

نموذج خرج مُتحقَّق منه فعليًا في هذه البيئة:

```
tables / rows        81 / 6737
artifact sha256      cd07baed410c0ffc9aab23e102d3d73adc7d3300b4cb61bad1aa03d1de7af420
status               verified
✓ content            81 tables / 6737 rows reproduce their hashes
✓ referential_integrity  all 149 foreign keys are satisfied inside the snapshot
restore drill: ✓ row_counts ✓ journal_balance (351 posted entries) ✓ tenant_partitioning
               ✓ row_sampling (15/15) ✓ audit_integrity (1353 rows) ✓ isolation
```

> **قاعدة صريحة:** لا تُسمّى نسخة «متحقَّق منها» إلا بعد قراءة الملف فعليًا ومطابقة التجزئة.
> أي فحص لا يستطيع العمل يُسجَّل `skipped` ولا يُسجَّل نجاحًا. وفي هذه البيئة لا يوجد
> `pg_dump/psql`، فالمسار المستخدم هو `logical-json` (يسجّله `backup_runs.format`)، بينما يختار
> المشغّل مسار `pg_dump --format=custom` تلقائيًا عند وجوده.

المهام الخلفية (pg-boss) عند `ENABLE_WORKER=true`: `heartbeat`، `zatca-submission`، `backup-run`،
`backup-verify`، `backup-drill`، `backup-prune`، و`platform-maintenance` (يوميًا 01:15:
تنظيف احتفاظ المساعد ثم فحص حداثة النسخ الاحتياطي).

## 6. استكشاف الأخطاء الشائع

| العَرَض | السبب المرجَّح | الحل |
|---|---|---|
| «جلسة غير صالحة» أو تحويل مستمر إلى `/login` | جلسة منتهية (12 ساعة) أو كوكي من نطاق آخر | أعد تسجيل الدخول؛ تأكد من استخدام `hisab_session` للمنشأة و`hisab_platform_session` للمنصة |
| «المنشأة في وضع القراءة فقط» | المنشأة موقوفة/معطَّلة أو الاشتراك منتهٍ | من المنصة: أعد الحالة إلى «نشِطة» — لا تفقد أي بيانات |
| «الصلاحية غير كافية» عند تنفيذ إجراء | دور المستخدم لا يحمل صلاحية الإجراء | أضف الصلاحية للدور (المساعد مثلًا يحتاج صلاحية الإجراء لاعتماد الطلب) |
| فاتورة لا تُرسل لـ ZATCA | لا شهادة إنتاج (pCSID) أو رمز OTP منتهٍ أو انقطاع | أكمل دورة `/tax`: مفتاح → OTP → الفحوص الستة → pCSID، ثم أعد الإرسال من «إعادة المحاولة» |
| «النسخ الاحتياطي قديم» في `/api/health` | تجاوزت آخر نسخة ناجحة النافذة (4 ساعات افتراضيًا) | `npm run backup:run` ثم `npm run backup:verify` |
| المساعد يجيب «المساعد غير متاح» | معطَّل على المنصة/المنشأة، أو اسم المتغير غير موجود في بيئة الخادم، أو لا يوجد مزوّد/موديل | راجع `/platform/flags` ثم `/assistant/settings` وتأكد من وجود قيمة للمتغير في `.env` وإعادة تشغيل الخادم |
| فشل ترحيل قيد | ربط حسابي ناقص، أو الفترة مغلقة، أو مجموع مدين ≠ دائن | افتح شاشة الربط، وتأكد من الفترة، وصحّح توازن القيد (رسالة الخطأ تحدّد السبب) |
| تعذّر تعديل فاتورة مُرحَّلة | قاعدة ثبات المستندات | أنشئ مرتجعًا أو قيدًا عكسيًا بتاريخ لاحق |
| `dialect`/`database does not exist` أثناء التطوير | قاعدة التطوير المدمجة توقفت | أعد تشغيل `node scripts/dev-postgres.mjs --dir .pglite` |

## 8. حدود هذا الإصدار (لا تُقرأ الجدولة كأنها إنجاز)

1. **ZATCA**: لم تُنفَّذ مصافحة كاملة مع بوابة فاتورة لعدم وجود بيانات اعتماد (AC-025). كل قواعد
   البنية والتوقيع والتحقق مُختبَرة محليًا فقط.
2. **المساعد الذكي**: لا يوجد تبادل حقيقي مع مزوّد في هذه البيئة (المفتاح المُهيَّأ قيمة تجريبية)،
   ولا بثّ للجواب (Streaming)، ولا إدخال مرفقات مستندات. القياس عددي فقط (لا حساب تكلفة).
3. **تصدير PDF** غير مُنفَّذ (Excel فقط).
4. **تقارير ناقصة المصدر** تظهر بحالة «غير متاح» صراحةً (منها R-05، R-10، R-12، R-24، R-27،
   R-46…R-51) ولا تُخمَّن أرقامها.
5. **أسئلة قانونية مفتوحة** (OQ-2/OQ-3/OQ-4) لم تُحسم في الكود ولم تُملأ بافتراضات.
6. المرحلة 10 (تشطيب الواجهات، جاهزية الإصدار) جارية؛ تقرير الجاهزية التفصيلي في
   `docs/RELEASE_READINESS.md`.
